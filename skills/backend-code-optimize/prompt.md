
# 专家评审 → 按意见优化 → 验证不变

先以资深工程师 / Tech Lead 视角出具**可执行的代码评审意见**，再严格按意见做行为不变的修改，最后验证功能流程与优化前一致。禁止跳过评审直接改代码，也禁止只出评审不落地（用户明确只要评审时除外）。

```
- [ ] Phase 1 划定范围与行为基线
- [ ] Phase 2 出具专家代码评审意见（只评不改）
- [ ] Phase 3 按评审意见逐项落地
- [ ] Phase 4 验证功能不变
```

评审维度细则、注释/拆分模板见 [reference.md](reference.md)。

## 核心原则

1. **评审驱动** — 改什么、改到什么程度，一律以 Phase 2 评审意见为准；未写入评审的改动禁止做
2. **行为不变** — 输入相同 → 输出相同；API 契约、数据流、用户可见流程不得改变
3. **专家标准** — 按资深工程师审 PR 的标准写意见：有位置、有问题、有为什么、有改法；禁止「不够优雅」「建议优化」这类空话
4. **不为改而改** — 找不到实质问题就写「可维护性已达标」并结束；禁止硬拆方法、硬堆废话注释凑项
5. **最小 diff** — 每次改动聚焦一个文件或一个职责域，便于审查与回滚
6. **自己验证** — 必须跑构建/接口/关键路径，不得仅凭「逻辑等价」宣称通过

## Phase 1：划定范围与行为基线

### 1.1 明确优化范围

从用户描述确定：

| 要素 | 示例 |
|------|------|
| 目标文件/目录 | `backend/src/services/paperImport.js`；未指定则按模块分批 |
| 优化动机 | 评审后按意见重构；缺注释、大函数、风格不统一 |
| 边界 | 只改实现与注释，不动路由签名与 DB schema |

范围不清时：优先**单模块、单文件**。用户明确「全局」时，按模块优先级分批执行，每批走完 Phase 1→4 再下一批，禁止一次扫改全仓库。

用户只要评审、明确不要改代码时：完成 Phase 1–2 后停止，把评审意见作为最终交付。

### 1.2 建立行为基线

优化前记录「当前行为」，作为 Phase 4 对照：

- 公共 API / 路由的入参、出参、状态码
- 关键分支（空值、错误、权限）的预期结果
- 若有现成测试或 curl 用例，先跑一遍留存输出

```markdown
## 行为基线
- `POST /api/internal/import-papers`：papers 为空 → 400；正常 → `{ imported, skipped }`
- `importPapers()`：analyze=true 时调用 AI 分析；false 时跳过
```

### 1.3 记录范式基线

动手前从同模块/同层已有代码归纳**当前主流范式**（落地只能向它对齐，不得另起一套）：

- 命名（驼峰/下划线、动词前缀、布尔 `is/has/can`）
- 分层（Controller 不写业务、Service 不写 SQL 细节等项目既有约定）
- 错误处理（抛异常 vs 返回 Result、日志级别）
- 注释语言与格式（中文/英文、JavaDoc/JSDoc）
- 导入顺序、空值处理、常量放置位置

### 1.4 Phase 1 出口条件

- [ ] 优化范围已划定
- [ ] 关键行为基线已记录（至少 2–3 条）
- [ ] 当前模块编码范式已归纳

## Phase 2：出具专家代码评审意见

**本阶段只评审，不改代码。** 以即将合并这段代码的资深工程师身份写意见。

### 2.1 评审角色

- 关注可维护性、可读性、可测试性、失败路径、抽象是否合适，同时警惕过度设计
- 每条意见必须让另一个工程师能直接改：文件 + 位置 + 问题 + 原因 + 改法 + 行为影响
- 疑似业务缺陷、契约变更、权限/查询语义问题：记入「仅记录不改」，不当作优化项

### 2.2 评审维度

按下列维度读代码（有问题才立项，允许某维度「无问题」）：

| 维度 | 专家在看什么 |
|------|----------------|
| 正确稳健 | 空值、资源关闭、失败路径、并发误用；仅行为等价的稳健性可改 |
| 结构职责 | 大函数、校验/IO/业务混杂、分层泄漏、编排方法堆细节 |
| 抽象重复 | 复制粘贴逻辑、错误抽象、该抽未抽或过度抽象 |
| 命名意图 | 名不副实、同层 `get/fetch/load` 混用、布尔非 `is/has/can` |
| 错误日志 | 吞异常、错误信息不统一、日志无业务主键、空 catch |
| 注释可读 | 公共方法缺业务说明；复杂分支缺「为什么」；废话/过时注释 |
| 范式一致 | 与邻居文件风格分裂、魔法值、嵌套 >3 层、卫语句缺失 |
| 可测试性 | 纯校验/映射/计算困在大方法里，无法独立验证 |
| 过度设计 | 无收益的接口/一层包装/为拆而拆 — 应建议合并或保持 |

扫描手段：`wc -l`、按语言搜函数定义，结合 `Read`/`Grep` 读调用链。有 graphify 时先 `query/explain/affected`。细节清单见 [reference.md](reference.md)。

### 2.3 严重级别（决定是否落地）

| 级别 | 含义 | Phase 3 |
|------|------|---------|
| **Must** | 明确损害可维护性/可读性/稳健性，且可行为等价修复 | 必须改 |
| **Should** | 资深工程师审 PR 会要求改的结构、范式、注释问题 | 必须改 |
| **Could** | 锦上添花；收益低或 diff 大 | 默认可跳过，跳过须说明 |
| **Note** | 疑似 bug、契约/权限/查询语义问题 | **只记录，禁止改** |

### 2.4 输出评审意见

必须先完整写出下列评审，再进入 Phase 3。

```markdown
## 代码评审意见

**视角**：资深工程师 / Tech Lead
**范围**：`<文件或目录>`
**总体评价**：1–3 句（结构是否清楚、主要风险、值不值得动）

### Must
1. **[结构职责]** `XxxService.java` `deploy` ~L80
   - 问题：180 行内混杂校验、SSH、写库
   - 为什么：后续改发布流程极易漏副作用，也无法单测校验
   - 改法：公共入口保持签名，提取 `validateDeploy` / `runRemote` / `persistResult`
   - 行为影响：无（纯提取，副作用顺序不变）

### Should
2. **[注释可读]** `XxxService.java` `executeDeploy` ~L12
   - 问题：公共方法无业务约束说明；超时分支看不出为何不重试
   - 为什么：调用方无法从签名得知「已成功单据会被拒绝」
   - 改法：补 JavaDoc；超时分支补「为何失败而非重试」的行内注释
   - 行为影响：无

### Could
（可空；空则写「无」）

### Note（仅记录不改）
- `deploy` 在远程成功但写库失败时可能重复发布 — 属业务语义，本次不改

### 不做项
- 不改公共方法签名与返回值结构
- 不改 DB schema / 查询语义
```

合格标准：

- 每条都有维度标签、位置、问题、为什么、改法、行为影响
- 总体评价必须具体；代码已经干净时允许 Must/Should 为空，并写明「无需优化，停止」
- 禁止用「三大能力各凑一条」来制造伪问题

### 2.5 Phase 2 出口条件

- [ ] 评审意见已完整输出（含总体评价 + 分级列表 + 不做项）
- [ ] Must/Should 每条均可执行；Note 已排除业务变更
- [ ] 无实质问题则宣布停止，不进入 Phase 3

## Phase 3：按评审意见落地

只实现 Phase 2 的 **Must** 与 **Should**。Could 默认跳过（除非收益明确且风险低）。Note 一律不改。

实施顺序：低风险（注释、常量、导入、删除过时注释）→ 提取纯函数 → 拆分大方法并对齐范式。每改一个文件 → `ReadLints`。

### 3.1 允许 / 禁止

**允许（不改变行为）：** 提取方法、重命名局部/私有符号、消除重复、早返回、补充业务注释与行内注释、删除错误注释、常量提取、导入整理、对齐同模块错误处理/日志写法。

**禁止：** 改 API 路径/字段/状态码语义；改查询条件、过滤、排序；改权限流程；改默认值含义；顺手加功能；为「简洁」删错误处理或日志；拆分时改变副作用执行顺序；评审未列出的「顺手重构」。

### 3.2 落地对照

改完必须能把评审条目勾到具体改动：

```markdown
## 评审落地对照

| # | 级别 | 评审摘要 | 落地 | 说明 |
|---|------|----------|------|------|
| 1 | Must | 拆分 `deploy` | 已落地 | 提取 `validateDeploy` / `runRemote` / `persistResult` |
| 2 | Should | 补 JavaDoc 与超时注释 | 已落地 | |
| 3 | Could | 再抽一层接口 | 跳过 | diff 大、收益低 |
```

### 3.3 注释、拆分、范式（按评审需要执行）

评审点到这些问题时，按 [reference.md](reference.md) 的模板落地：

- **注释**：业务注释写规则与失败语义；行内注释写「为什么」；禁止复述代码
- **单一职责**：公共入口保持原名与签名，内部编排；拆出 `validate*` / `build*` / `persist*` 等；不改变副作用顺序
- **范式**：向 Phase 1 归纳的本仓库主流写法对齐，不套教科书风格

未在评审中出现的维度不要主动扩 scope。

### 3.4 Phase 3 出口条件

- [ ] Must / Should 已落地或有跳过理由（Should 原则上不跳过）
- [ ] 落地对照表已填写
- [ ] 无新增 linter 错误
- [ ] 公共 API 签名与 Phase 1 基线一致
- [ ] diff 中无评审未覆盖的逻辑改动

## Phase 4：验证功能不变

### 4.1 验证策略

| 检查项 | 做法 |
|--------|------|
| 行为对照 | 按 Phase 1 基线重跑 curl / 页面操作，对比输出 |
| 构建 | 前端 `npm run build`；后端编译/启动无 crash |
| 类型/lint | `ReadLints` 改动文件 |
| 回归路径 | 走一遍主流程（登录 → 列表 → 详情 → 关键 mutation） |
| diff 审查 | 每处逻辑改动都能回溯到某条评审；注释与代码一致 |

### 4.2 验证报告

```markdown
## 优化验证报告

| 基线项 | 优化前 | 优化后 | 结果 |
|--------|--------|--------|------|
| … | … | … | ✅ |

**结论**：行为不变 / 存在偏差（列出并回滚修复）
```

### 4.3 Phase 4 出口条件

- [ ] 所有基线项验证通过
- [ ] 验证报告结论为「行为不变」

**有偏差 → 回滚或修正 Phase 3，重新验证。**

## 最终汇报模板

```markdown
## 代码优化完成

**范围**：`<文件/目录>`
**原则**：专家评审驱动；行为不变；只落地 Must/Should

### 评审摘要
- 总体评价：…
- Must n / Should n / Could n / Note n

### 主要落地
1. …
2. …

### 验证
✅ 行为基线全部通过，功能流程不受影响

### 变更文件
- `path/to/file`
```

Phase 2 判定无需优化时，汇报「评审结论：无需改动」+ 总体评价，不要空提交 diff。

用户要求提交时，使用 `@backend-code-commit`。

## 触发示例

| 用户输入 | 执行方式 |
|----------|----------|
| `@backend-code-optimize backend/src/services/paperImport.js` | Phase 1→4，限定单文件 |
| `先评审再按意见改` | 先完整输出评审，再落地 Must/Should |
| `只要评审意见，先别改` | 只做 Phase 1–2 |
| `优化这段代码，不要改逻辑` | 评审 + 行为不变落地 |
| `重构一下，加注释` | 评审后按意见拆分/补注释，不为凑项而改 |
| `全局代码优化` | 按模块分批，每批 Phase 1→4 后再下一批 |

---

## 禁止事项

- ❌ 未写完整评审意见就改代码
- ❌ 未建行为基线就重构
- ❌ 评审意见空泛（无位置、无原因、无可执行改法）
- ❌ 为凑「注释/拆分/范式」三条而制造伪问题
- ❌ 修改业务分支逻辑、默认值、API 契约
- ❌ 落地 Note（疑似 bug / 契约问题）或评审未列出的改动
- ❌ 拆分方法时改变副作用执行顺序
- ❌ 用个人偏好覆盖仓库已有编码范式
- ❌ 未验证就宣称「功能不受影响」

## 输出与收尾（eng-code-skills 统一）

完成工作流后，汇报中必须包含：

### 风险警告（必填）
列出未覆盖风险、不确定假设、可能影响生产的点；对修复/实现类任务，标明回归范围。

### 人工校验点（必填）
给出可执行检查清单（构建、接口、关键路径、停服/资源确认等）。
