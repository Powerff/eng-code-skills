# 后端项目 / 服务重构（Backend Project Refactor）

方法论参考：[一个Skill搞定服务重构：从链路分析到测试自动化](https://mp.weixin.qq.com/s/kHpDP4yQoj5Vr0xGk2TDLg)（腾讯云开发者）。本技能将其泛化为可落地的前后端项目重构工作流，不绑定原文中的 C++ / tRPC-Go 技术栈。

## 核心判断

**重构 ≠ 一比一代码搬运。**  
真正的成本是：把多年散落在调用链里的业务逻辑（状态机分支、隐式校验、数据依赖、历史补丁）梳理清楚，再用目标架构重新表达。能信的往往只有代码本身。

老服务业务规则通常散落在：

- **状态机分支**：多层 switch/case，各有前置条件
- **隐式校验**：必传字段、限流、签名/票据、格式校验与主流程交织
- **数据依赖**：分表、缓存反查、下游 RPC、MQ；一次请求牵动多表多系统
- **历史包袱**：兼容补丁、绕过 bug 的临时代码，常无注释

## 老链路四层模型（分析时必须按此展开）

1. **入口层**：收包/鉴权/解密/验签/限流/报文解析/单号反查等前置；字段来源影响后续分支
2. **编排层**：顺序调用下游并聚合决策；含跨调用隐式契约（票据、幂等键等）
3. **核心业务层**：加锁读状态 → 按状态/金额等进入多分支写入；每分支字段更新规则不同
4. **查询层**：决定上游数据口径；字段对不齐则整条链路判断错误

分析时**不能只看调用关系**，必须深入方法内部，展开到 DB / 缓存 / RPC / MQ，并记录：

- 每个关键字段的真实来源（入参 / 反查 / 常量）
- 每个分支的前置条件

## 五阶段流程（不可跳步）

```
- [ ] Phase 1 链路分析 & 生成方案
- [ ] Phase 2 审查方案（人主导）
- [ ] Phase 3 实施编码
- [ ] Phase 4 代码 CR / 完整性评估
- [ ] Phase 5 自动化测试闭环
```

### Phase 1：链路分析 & 生成方案

1. 读/补 `project-config.md`；隔离依赖代码（如 `../_refactor_deps/` 或只读路径），勿污染工作区。
2. 按四层追踪完整调用链，深入方法内部至最终副作用。
3. **能力 GAP 分析**：老链路所需下游能力 vs 目标服务已有 API/Proto/DTO，列缺口与补齐方式。
4. 生成方案（参见 `references/document-template.md`），至少含：链路概述、原始调用链、数据依赖、**归属映射**、协议定义、实现方案、关键迁移点、配置变更、优先级、测试与风险。
5. **完整性自检**：章节齐全、旧步骤均有归属、状态机分支列全。

**出口**：方案草稿 + GAP 表 + 归属映射；未过完整性自检不得进入 Phase 2。

### Phase 2：审查方案（人机协作最密）

人工重点：

- 归属映射是否正确（编排 vs 领域 vs 基础设施）
- 协议字段是否完整
- 状态机分支是否遗漏
- GAP：新增接口还是扩展已有接口
- 废弃分支 / 可删字段 / 灰度维度（代码读不出来的，必须问人）

AI 把取舍整理成**选择题**，每轮最多 5 问；结论写入 `clarifications.md`。

**出口**：人确认方案与协议；未确认禁止编码。

### Phase 3：实施编码

前置：方案审查通过；协议/桩代码已就绪（若项目需要）。

- 按项目/模块逐个落地，遵循方案分层（示例：Gateway → Service → Logic/Domain → Repo）
- **领域实体不依赖**框架协议类型；Repo 通过接口隔离
- 编排可用可插拔步骤（Builder / Pipeline）；旁路校验失败可降级为监控而非卡死主流程（若业务允许且方案已写明）
- **验证循环**：每完成一个逻辑单元 → build / lint / 结构检查 → 通过再继续；同错修 3 次不过交人

**禁止**：擅自改业务语义、静默删除分支、扩大方案外范围。

### Phase 4：代码 CR

按 `references/code-review-checklist.md` 三维自查：

1. **设计**：分层、依赖方向、接口隔离
2. **实现**：错误包装、日志/trace、Context 透传、事务/锁
3. **规范**：命名、注释、import、项目既有范式

并做**重构完整性评估**：方案章节是否落全、归属映射逐步有代码、状态机全覆盖、协议与方案一致。

### Phase 5：自动化测试闭环

目标：真实运行行为与老服务关键路径一致。

1. 构建 / 部署（按项目惯例）
2. 编写/复用 client 或集成测试，按场景切换
3. **构造数据**：优先复用库内真实记录并重置状态，勿凭空造敏感交易数据
4. 自动修复循环：跑测 → 查日志/链路 → 改 → 重部署 → 重测（最多 5 轮）
5. 超限：汇总未解问题交人

## 何时使用

- 后端服务迁移 / 微服务拆分 / 分层改造 / 跨语言重写前的链路梳理与落地
- 用户提到：服务重构、链路分析、DDD 落地、协议 GAP、重构方案、@backend-project-refactor


## Harness 保障机制（全程强制）

参考 Harness Engineering：模型能力是商品化输入，**编排 / 验证 / 可观测 / 成本 / 可追溯**决定可靠性。

1. **知识加载精准**：渐进式披露；当前阶段只读本阶段所需 references，禁止一次性塞满上下文。
2. **流程不中断**：五阶段线性推进；每阶段「人发起 → AI 执行 → 人审查 → 再推进」；允许回退到上一阶段。
3. **结果有校验**：分析要有完整性检查；编码要有单元级验证循环；CR 要有清单；测试要有真实运行证据。
4. **成本不失控**：
   - 同一文件单阶段最多精读 **2** 次
   - 参考项目 / 参考模块最多查 **3** 个
   - 同一编译/类型错误连续修 **3** 次仍不过 → 停下交人
   - 测试自动修复循环最多 **5** 轮 → 超限汇总交人
   - 每轮澄清问题最多 **5** 个
5. **过程可追溯**：决策写入 `clarifications.md`；方案、归属映射、GAP 表、测试记录落盘可交接。
