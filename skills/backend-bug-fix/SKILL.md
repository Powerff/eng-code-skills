# 问题定位 → 修复 → 验证

接收到问题描述之后，先定位问题，再修复验证。**未完成定位，禁止动手改代码。**

```
- [ ] Phase 1 理解问题
- [ ] Phase 2 定位根因
- [ ] Phase 3 修复
- [ ] Phase 4 验证
```

## 核心原则

1. **先定位，后修复** — 根因未确认前，不提交任何修复代码
2. **用证据说话** — 日志、复现步骤、调用栈、接口响应，至少一项支撑结论
3. **最小修复** — 只改根因相关代码，不顺手重构
4. **自己验证** — 必须实际复现/回归，不得仅凭「应该好了」收尾
5. **说清因果** — 汇报时说明「现象 → 根因 → 修复 → 验证结果」

---

## Phase 1：理解问题

### 1.1 提取问题要素

从用户描述中整理：

| 要素 | 内容 |
|------|------|
| 现象 | 用户看到了什么（报错信息、空白页、数据错误等） |
| 预期 | 正确行为应该是什么 |
| 触发条件 | 操作路径、环境（本地/254/Docker）、账号角色 |
| 范围 | 前端 / 后端 / agent-service / 部署 / 数据库 |
| 时间 | 一直存在 / 最近才出现 / 某次部署后 |

信息不足时，**只问关键缺失项**（1–2 个问题），不要连环追问。

### 1.2 定义复现标准

用一句话写清「怎样算复现成功」：

> 例：访问 `/bio/papers/xxx` 时摘要中文翻译不显示，API 返回 `abstractZh: null`。

### 1.3 Phase 1 出口条件

- [ ] 现象、预期、触发条件已明确
- [ ] 有可操作的复现/检查标准

---

## Phase 2：定位根因

**本阶段只做调查，不改业务代码**（临时 debug 日志除外，且验证后须移除）。

### 2.1 复现问题

按触发条件实际操作或调用：

```bash
# 查看服务日志
docker compose logs -f backend --tail=100

# API 复现
curl -sv http://localhost:3001/api/...

# 前端构建/类型检查
cd frontend && npm run build
```

记录：HTTP 状态码、错误堆栈、响应体、控制台报错。

### 2.2 缩小范围

按层级自上而下排查：

```
用户操作 → 前端请求 → 网关/路由 → 控制器 → 服务层 → 数据库/外部 API → 配置/环境变量
```

常用手段：

| 手段 | 适用场景 |
|------|----------|
| `Grep` / 搜索报错关键字 | 快速找到抛出异常的代码 |
| 读调用链上下游文件 | 理解数据如何流转 |
| 查 `.env` / `docker-compose.yml` | 配置缺失或端口错误 |
| 查 `prisma/schema` + 实际数据 | 字段为空、类型不匹配 |
| 查最近 `git log` / `git diff` | 回归引入 |

### 2.3 确认根因

输出**定位报告**（必须写，再进入 Phase 3）：

```markdown
## 定位报告

### 现象
<用户看到的问题>

### 复现步骤
1. ...
2. ...

### 调查发现
- <证据 1：如 curl 返回 500，错误信息 xxx>
- <证据 2：如 translateService 未被调用>

### 根因
<一句话：哪个文件的哪段逻辑在什么条件下导致了问题>

### 修复思路
<拟改什么、为什么能解决问题>
```

### 2.4 常见根因速查

| 症状 | 优先检查 |
|------|----------|
| 500 / 未捕获异常 | 服务日志、`GlobalExceptionHandler`、async 未 await |
| 401 / 403 | JWT、`internalAuth`、`x-internal-key` |
| 数据为空 | Prisma 查询条件、seed 数据、字段名映射 |
| 前端白屏 | 浏览器控制台、`npm run build` 类型错误 |
| Docker 启动失败 | `docker-entrypoint.sh`、环境变量、DB 连接 |
| 仅生产环境复现 | 254 部署配置、CI workflow、nginx 路径 |

### 2.5 Phase 2 出口条件

- [ ] 问题已复现或有充分证据解释无法复现
- [ ] 根因已定位到具体文件/逻辑/配置
- [ ] 定位报告已输出

**根因不确定 → 继续调查，不得进入 Phase 3。**

---

## Phase 3：修复

### 3.1 修复原则

- 针对根因做**最小改动**
- 匹配项目既有风格（命名、错误处理、日志格式）
- 不引入无关重构
- 若需改 schema / 环境变量，同步更新 `.env.example` 并说明

### 3.2 修复后自检

- `ReadLints` 检查改动文件
- 移除 Phase 2 临时 debug 代码
- 能一句话说明「改了什么、为什么能修」

### 3.3 Phase 3 出口条件

- [ ] 修复代码已落地
- [ ] 无新增 linter 错误
- [ ] 无临时调试代码残留

---

## Phase 4：验证

### 4.1 验证清单

| 检查项 | 做法 |
|--------|------|
| 原问题复现路径 | 按 Phase 1 步骤重走，确认现象消失 |
| 修复有效性 | 接口/页面返回预期数据或状态 |
| 回归 | 相邻功能未破坏（auth、列表、分页等） |
| 构建 | 改了前端则 `npm run build`；改了后端则确认服务启动 |
| linter | 改动文件无新错误 |

### 4.2 本项目常用命令

```bash
curl -s http://localhost:3001/api/health
cd frontend && npm run build
cd backend && npm run dev   # 确认无 crash
docker compose logs backend --tail=50
```

### 4.3 验证报告

```markdown
## 验证报告

| 检查项 | 结果 | 说明 |
|--------|------|------|
| 原问题复现 | ✅/❌ | 按原步骤操作，问题已消失 |
| 预期行为 | ✅/❌ | ... |
| 回归 | ✅/❌ | ... |
| linter | ✅/❌ | ... |

**结论**：通过 / 未通过
```

### 4.4 Phase 4 出口条件

- [ ] 原问题不再复现
- [ ] 验证报告结论为「通过」

**未通过 → 回到 Phase 2 重新定位，或 Phase 3 调整修复。**

## 最终汇报模板

```markdown
## 问题修复完成

**问题**：<一句话>
**根因**：<一句话>
**修复**：`<文件>` — <做了什么>
**验证**：✅ 原路径复现通过 / 回归通过

### 变更文件
- `path/to/file`: ...
```

用户要求提交时，转用 `@backend-code-commit` 或 `@backend-implement-verify-commit` 完成 commit + push。

## 触发示例

| 用户输入 | 执行方式 |
|----------|----------|
| `@backend-bug-fix 论文详情页翻译不显示` | Phase 1→2→3→4 |
| `帮我排查 internal 接口 500` | 同上 |
| `这个报错是什么意思`（仅解释） | 只 Phase 1–2，输出定位报告，不自动改代码 |
| `@backend-bug-fix ... 修完提交` | Phase 1–4 后接 `@backend-code-commit` |

---

## 禁止事项

- ❌ 未定位根因就改代码
- ❌ 只看报错首行就下结论
- ❌ 用 try-catch 吞掉异常当作修复
- ❌ 未复现就宣称已修复
- ❌ 修复时大范围重构无关代码
- ❌ 遗留临时 console.log / print 调试代码

---

## 输出与收尾（eng-code-skills 统一）

完成工作流后，汇报中必须包含：

### 风险警告（必填）
列出未覆盖风险、不确定假设、可能影响生产的点；对修复/实现类任务，标明回归范围。

### 人工校验点（必填）
给出可执行检查清单（构建、接口、关键路径、停服/资源确认等）。
